# Serena 接入与 Codex 提效规则：完整对话复盘

## 一句话结论

本次对话完成了 Serena 在 Codex 中的接入认知、状态验证和项目规则建设。最终形成的工作方式是：**新会话按真实工具调用报告 Serena 四项状态；索引未就绪时持续轻量复查；代码查询采用“最小充分证据 + 明确停止条件”；用户请求采用自适应确认，而不是每次机械追问。**

## 背景与目标

最初目标是根据内部 Serena 文档完成接入，并解决以下实际问题：

1. Serena 接入后究竟改变了什么。
2. 如何确认 Serena 真实连接、项目激活、语言后端和索引可用。
3. 切换项目或 Git 分支后如何重新加载。
4. 为什么新会话没有按约定报告 Serena 状态。
5. 为什么已经启用 Serena，查询接口仍需 2～5 分钟。
6. 如何通过 `AGENTS.md` 让后续会话更稳定、更高效。
7. 是否应该在每次执行前先优化用户提示词并确认。

参考文档：<https://globaldocs.atlassian.net/wiki/spaces/crmdocs/pages/802848776/Serena>

## 对话时间线与证据

### 1. 使用终端验证时出现 `codex: command not found`

用户最初尝试在 macOS 终端中运行：

```shell
codex mcp get serena
```

终端返回：

```text
zsh: command not found: codex
```

![终端中 codex 命令不可用](<assets/Serena 接入与 Codex 提效规则/01-codex-cli-not-found.png>)

#### 这张截图说明什么

它只说明当前 shell 中没有可执行的 `codex` 命令，或该命令没有加入 `PATH`。它**不能**证明：

- Codex 桌面应用没有运行；
- Serena MCP 没有配置；
- Serena 未连接；
- Serena 索引失败。

Codex 桌面应用中的 MCP 能力和终端 CLI 是不同入口。正确验证方式应以当前会话实际暴露的 Serena 工具及真实调用结果为准。

### 2. 新会话没有出现约定的 Serena 状态

用户随后开启新会话查询“余额调整批量审核接口”，回答直接给出了接口信息，但没有显示约定的 Serena 状态行。

![新会话未显示 Serena 状态](<assets/Serena 接入与 Codex 提效规则/02-new-session-missing-status.png>)

#### 暴露的问题

仅在对话里口头约定规则不够稳定。新会话是否继承要求，取决于规则是否落在该项目可读取的 `AGENTS.md` 作用域内。

此外，状态规则必须明确要求出现在**首次最终回答的第一行**。如果只写在过程消息、工具输出或可折叠的进度区域，用户仍可能看不到。

#### 形成的修正

新会话首次最终回答固定使用：

```text
Serena 连接：<已连接|未暴露|失败> | 项目：<项目名|未激活> | 语言后端：<后端|不可用> | 索引：<已就绪|初始化中|未验证>
```

并且必须先执行真实检查，不能用推断填充状态。

### 3. 首次优化前：单接口查询耗时 4 分 53 秒

查询“操作实名认证结果”的接口时，最终答案已经包含 HTTP 方法和路径、参数、状态值、Controller、Client、Service 源码位置，以及文档注释与实际实现之间的差异。

但总耗时达到 **4 分 53 秒（293 秒）**。

![单接口查询耗时 4 分 53 秒](<assets/Serena 接入与 Codex 提效规则/03-single-api-4m53s.png>)

#### 为什么 Serena 已就绪仍然较慢

截图中的状态为“已连接 / tmd / LSP / 已就绪”，说明 Serena 本身可用。耗时主要来自查询深度，而不是连接失败：

1. 不只定位 Controller，还继续追踪 Client 和 Service。
2. 核对状态枚举、Swagger 描述和 JavaDoc 差异。
3. 为保证准确性进行了多轮交叉验证。
4. 输出内容超出了“确认接口”所需的最小范围。

Serena 提升的是符号导航效率，不会自动替用户决定“查到哪里停止”。

### 4. 加入快速路径后：同类查询降至 2 分 33 秒

调整 `AGENTS.md` 后，再次查询同类实名认证接口，耗时变为 **2 分 33 秒（153 秒）**。

![优化后单接口查询耗时 2 分 33 秒](<assets/Serena 接入与 Codex 提效规则/04-single-api-2m33s.png>)

#### 效果对比

| 场景 | 优化前 | 优化后 | 减少 | 降幅 |
|---|---:|---:|---:|---:|
| 单接口确认 | 293 秒 | 153 秒 | 140 秒 | 约 47.8% |

优化已经明显生效，但 2 分 33 秒仍不是纯定位时间。回答仍包含参数解释、状态值与示例，因此还有进一步压缩空间。

### 5. 查询“所有登录接口”耗时 3 分 25 秒

查询范围扩大为“所有登录接口”后，需要扫描多个 Controller、终端和版本，最终识别出 26 个唯一 HTTP 路由及 6 个登录辅助路由，耗时 **3 分 25 秒（205 秒）**。

![全部登录接口查询耗时 3 分 25 秒](<assets/Serena 接入与 Codex 提效规则/05-all-login-apis-3m25s.png>)

#### 为什么比单接口慢是合理的

“所有登录接口”不是一个符号定位问题，而是一个集合边界问题，需要判断：

- “登录”是否包含验证码发送；
- 是否包含账户检测、二次认证和登录态刷新；
- APP、H5、管理端是否全部纳入；
- 相同路径的不同版本是否算一个接口；
- 是按 Controller 声明统计，还是按网关最终路由统计。

Serena 可以加速找到候选符号，但仍需语义筛选与去重。因此，广范围清单任务的耗时不能与单接口定位直接比较。

## Serena 的真实作用

### Serena 擅长的事情

- 按类、方法、字段和符号名称定位代码。
- 查找定义、引用和调用关系。
- 在大型项目中减少逐文件全文扫描。
- 从 Controller 精确跳到 Service、Client 或实现类。
- 在索引就绪后提供比纯文本搜索更可靠的结构化结果。

### Serena 不会自动解决的事情

- 不会自动定义“全部”“相关”“登录接口”等业务边界。
- 不会保证索引在项目激活后立刻完成。
- 不会替代对注解、配置、网关和运行时行为的判断。
- 不会自动停止过度调查。
- 不会让长篇输出、表格整理和完整业务分析变成零成本。

| 任务类型 | 预期收益 | 原因 |
|---|---|---|
| 定位单个类或方法 | 很高 | 可直接符号查询 |
| 查找接口入口 | 高 | Controller 和映射注解范围明确 |
| 追踪调用链 | 高 | 引用关系比全文搜索更准确 |
| 枚举所有业务接口 | 中等 | 仍需定义范围、筛选和去重 |
| 理解运行时配置 | 中低 | 可能涉及配置中心、网关或外部系统 |
| 生成长篇报告 | 低 | 主要成本在组织和表达 |

## 四项状态必须分开判断

| 状态 | 要回答的问题 | 验证依据 |
|---|---|---|
| 连接 | 当前会话能否调用 Serena MCP | 至少一次 Serena 工具调用成功 |
| 项目 | Serena 当前激活的是哪个项目 | 当前配置返回的真实项目 |
| 语言后端 | 当前使用什么代码分析后端 | 当前配置返回的后端，例如 LSP |
| 索引 | 能否实际返回符号结果 | 轻量只读符号查询成功 |

### 常见错误推断

- MCP 已连接 ≠ 项目已激活。
- 项目已激活 ≠ 语言后端已启动。
- 语言后端存在 ≠ 索引已完成。
- 索引未完成 ≠ 项目未激活。
- 顶层工具列表未显示 Serena ≠ Serena 未暴露；还需检查延迟工具注册表。

### 推荐状态机

```text
检查工具暴露
    ↓
调用 Serena 成功 ──否──> 失败或未暴露
    ↓ 是
激活当前项目
    ↓
读取当前配置
    ↓
执行一次轻量符号查询
    ├─ 成功返回符号 → 索引已就绪
    ├─ 后端启动中/超时 → 索引初始化中
    └─ 无合适文件可查 → 索引未验证
```

## 新会话初始化规则

新会话第一次实质回答前，应按以下顺序处理：

1. 检查直接暴露的工具。
2. 检查延迟工具注册表中的 `mcp__serena__*`。
3. 如果工具可用，激活当前项目。
4. 调用 Serena 的初始说明。
5. 获取当前配置，读取真实项目和语言后端。
6. 选择一个相关源文件，最多执行一次轻量、只读的符号查询。
7. 在第一次**最终回答首行**输出中文四状态。
8. 不为了等待索引而阻塞用户的主要任务。

如果索引处于“初始化中”或“未验证”，后续每轮用户请求开始时最多复查一次。首次查询成功后，在该轮最终回答中额外显示一次：

```text
Serena 索引已就绪：现在可以对 <项目名> 使用语义代码导航。
```

这比“经过固定 N 轮再检查”更可靠，因为索引完成取决于项目大小、缓存、语言服务器状态和机器负载，而不是对话轮数。

## 项目与分支切换

### 打开不同项目

必须重新执行完整初始化：激活新项目、读取当前配置、确认语言后端、用新项目源文件验证索引，并重置索引就绪通知状态。

### 同一项目切换 Git 分支

1. 重新激活当前项目。
2. 将记忆中的索引状态重置为“初始化中”或“未验证”。
3. 重新执行一次轻量符号查询。
4. 在首次重新就绪时提示一次。

原因是分支切换可能增加、删除或重命名符号。即使语言服务器仍在运行，旧索引也不能直接作为当前分支的可靠证据。

## 代码查询提效策略

### 核心原则：先定义交付物，再决定调查深度

对于“帮我找接口”类请求，默认最小交付应是：

- HTTP 方法；
- 完整路径；
- 必要参数或请求体；
- Controller 源码位置。

只有用户明确要求 Service、远程 Client、数据库写入、状态枚举、完整调用链、影响范围或文档冲突时，才继续深入。

### HTTP 接口快速路径

```text
用户业务词
  → 限定模块与端
  → 搜索 Controller / RequestMapping
  → 读取类级路径 + 方法级路径
  → 提取参数
  → 找到唯一满足项
  → 停止
```

### 停止条件

满足用户交付范围后立即停止。只有缺少必要字段、存在多个合理候选、注释与实现冲突、用户要求完整业务分析，或当前证据不足时才继续。

### 工具选择顺序

1. 精确路径或明确文本：优先 `rg`。
2. 类、方法、引用、调用关系：优先 Serena。
3. Controller 映射枚举：先文本缩小候选，再用 Serena 验证符号。
4. 不对同一事实重复进行多套等价验证，除非结果冲突。

## 自适应确认规则

用户曾提出：是否每次提问后先询问一次、优化提示词，再执行。最终选择“自适应确认”，原因是机械确认会增加一轮交互，可能抵消 Serena 带来的时间收益。

### 内部归一化

收到请求后，先在内部识别目标、作用范围、期望输出、调查或修改深度、停止条件，以及是否涉及外部写入或不可逆风险。

### 直接执行

- 单个接口或符号查询；
- 范围明确的只读分析；
- 指定文件内的小改动；
- 普通解释或状态查询；
- 目标、输出和授权边界已经明确。

### 需要确认

只在缺失选择会实质改变结果时询问，并且一次最多问一个问题：

- 使用“所有、全面、完整”等词但没有定义边界；
- 存在多个同样合理的模块、分支或目标；
- 无法判断用户只要诊断还是也要修改；
- 涉及破坏性变更、外部写入或不可逆影响；
- 不同要求之间发生冲突。

### 用户控制词

- `极速`：采用最小充分范围，优先给结果。
- `先给结果`：先输出结论，必要解释后置。
- `不要确认`：在安全且授权明确时直接执行。
- `完整分析`：允许继续追踪调用链、边界和影响范围。

默认不展示冗长的“优化后提示词”，除非用户明确要求查看。

## 不同场景下的推荐提问模板

### 极速定位单个接口

```text
极速：在 tmd 中定位“操作实名认证结果”的 HTTP 接口。
只给请求方法、完整路径、参数和 Controller 源码位置；找到唯一匹配后停止。
```

### 枚举一组接口

```text
列出 be-spotec-aggr 中用于建立或推进登录态的接口。
范围仅限 Controller；包含 APP 和 H5；排除验证码发送、登出和登录后资料查询。
按端、方法、完整路径、参数和源码位置输出，并说明去重口径。
```

### 完整调用链

```text
定位“操作实名认证结果”接口，并追踪到 Service 和远程 Client。
说明关键调用链、type 状态值来源以及注释与实现冲突；不展开无关分支。
```

### 修改代码

```text
修改 <文件或方法> 完成 <目标>，保持现有接口兼容。
只改必要文件，运行最小相关测试，并报告修改点、风险和验证结果。
```

### 只诊断不修改

```text
诊断 <现象> 的原因，只做只读检查，不修改代码。
按“根因、证据、影响、建议”输出；找到可解释现象的直接证据后停止。
```

### 分支切换后继续工作

```text
我刚切换到 <branch>。请重新激活 Serena 项目并验证索引，然后再查询 <目标>。
```

## 验收清单

### Serena 状态

- [ ] 新会话第一次最终回答首行显示中文四状态。
- [ ] “已连接”来自真实 Serena 工具调用成功。
- [ ] 项目名称和语言后端来自当前配置。
- [ ] “已就绪”来自符号查询成功，而不是连接或激活推断。
- [ ] 索引未完成时显示“初始化中”或“未验证”，不误报“未激活”。
- [ ] 索引首次就绪时只提示一次。

### 项目、分支与效率

- [ ] 切换项目后重新完整初始化。
- [ ] 切换分支后重新激活并验证索引。
- [ ] 单接口查询默认止于方法、路径、参数和 Controller 位置。
- [ ] 用户未要求时，不主动展开完整调用链。
- [ ] “全部”类任务先明确纳入和排除标准。
- [ ] 找到满足交付范围的证据后停止。

### 自适应确认

- [ ] 清晰、低风险的问题直接执行。
- [ ] 关键歧义最多询问一个问题。
- [ ] 不机械复述或展示优化后的提示词。
- [ ] 用户说“极速”时采用最小充分范围。

## 最终经验

1. **不要把工具存在当成工具可用。** 必须进行真实调用。
2. **不要把项目激活当成索引完成。** 必须以符号查询验证。
3. **不要用固定对话轮数判断索引状态。** 应采用事件驱动的轻量复查。
4. **不要把“更完整”默认为“更好”。** 对接口查询，最小充分答案通常更快、更有用。
5. **Serena 解决定位问题，规则解决边界问题。** 两者结合才能稳定提效。
6. **自适应确认优于每次确认。** 只在选择真正影响结果时增加一轮交互。
7. **用截图记录耗时很有价值。** 本次案例显示快速路径让同类单接口查询从 293 秒下降到 153 秒，约减少 47.8%。
